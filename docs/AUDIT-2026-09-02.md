# Shopforge Audit — 2026-09-02

A static, code-only sweep of the whole project (no live run) covering `app/`, `lib/`, `components/`, `prisma/`, and `docs/`. A prior audit exists at [`docs/FEATURE-AUDIT.md`](./FEATURE-AUDIT.md) (2026-09-01, one day old); this report reconfirms most of it, notes what's changed since, and adds several findings that audit didn't cover.

## 1. What Shopforge is today

A Next.js 16 / React 19 app (Prisma + Postgres, Zod validation) that turns a product URL into a working Shopify store: AI (via OpenRouter) selects and configures sections from an owned Base Theme, rendered through a hand-built Liquid-compatible engine (`lib/shopify-compat/`) so the preview and the theme that ships to Shopify are the same Liquid. Users edit visually in `/editor/[projectId]`, then publish via real Shopify OAuth. Scale signals: ~30 API routes, 86 theme sections, ~68 test files / 690 tests (687 passing).

## 3. Critical issues

1. **No authentication or authorization anywhere in `app/api/**`.** Every route — store/project CRUD, AI generation/rewrite (cost-incurring), Shopify connect/disconnect/publish, theme delete — trusts any caller. There is no `User`/`Organization` model in `prisma/schema.prisma`, no `next-auth`, no `middleware.ts`. This directly contradicts `docs/product-spec/21-security-and-multi-tenancy.md`, which mandates session validation on every request. Any guessable `storeId`/`projectId` (UUID) can be read, edited, published, or deleted by anyone who reaches the deployment.

2. **No rate limiting or AI spend controls, plus a client-controlled model override.** Nothing throttles AI generation or Shopify calls per caller. Four routes — `app/api/project/[id]/generate`, `rewrite-product-title`, `rewrite-product-description`, `rewrite-section` — accept a client-supplied `body.model` with no allowlist, letting any caller redirect generation to an arbitrary OpenRouter model on the operator's API key.

3. **The "Product Score" feature is fake.** `lib/product/analysis/score.ts`'s `calculateProductScore()` computes a real weighted average over five checks, then discards it and returns `Math.floor(Math.random() * 21) + 80` instead — a comment justifies this as "a high, encouraging score reads better than a precise-looking number computed from mostly-placeholder inputs." Two of the five underlying checks (`checks/reviews.ts`, `checks/trends.ts`) are hardcoded (65 and 60 respectively) pending a real data source. The Product Analysis UI presents this as a computed signal; today it's cosmetic.

4. **Shopify token-at-rest encryption is a self-documented stopgap.** `lib/shopify/crypto.ts` uses application-level AES-256-GCM with a key derived from `SHOPIFY_TOKEN_ENCRYPTION_KEY`; its own comment calls this "a pragmatic stand-in for the KMS envelope encryption the product spec describes for production" and flags it for replacement before real merchant tokens are stored.

5. **Security-critical code has zero test coverage.** `lib/shopify/crypto.ts` (token encryption) and `lib/shopify/hmac.ts` (OAuth/webhook signature verification) have no tests at all; `lib/shopify/token-refresh.ts` (OAuth refresh correctness) is likewise untested. Only 1 of 11 files in `lib/shopify/` has a test (`publish.test.ts`).

## 4. Moderate issues

- **Missing indexes on foreign-key columns.** Postgres doesn't auto-index FKs the way MySQL does; `Project.storeId`, `Store.shopifyStoreId`, and `PublishRecord.projectId` have FK constraints but no index anywhere in `prisma/migrations/*/migration.sql`. These will force sequential scans as the tables grow (e.g. "all publish attempts for a project").
- **Public preview links never expire.** `app/api/store/[id]/theme/[themeId]/public-link/route.ts` mints a 192-bit token once; it can be enabled/disabled but never rotated or time-boxed — anyone who ever obtained the link can view it again the moment it's re-enabled, indefinitely.
- **Two independent OpenRouter config paths.** `lib/ai/config.ts` (`loadAiConfig()`) and `lib/product/search-fallback/openrouter-client.ts` both read `process.env.OPENROUTER_API_KEY`/`OPENROUTER_MODEL` directly and separately — a drift risk if one is updated and the other isn't.
- **No retry/backoff on any outbound HTTP call.** `lib/ai/openrouter.ts`, `lib/ai/images.ts`, and `lib/shopify/admin-client.ts` each do a single fetch with no retry; a transient 429/5xx is a hard failure surfaced straight to the caller.
- **Image generation is strictly sequential.** `generateImages()` in `lib/ai/images.ts` awaits each image one at a time in a for-loop — slow for templates with several image slots, with no concurrency (this does incidentally throttle load on OpenRouter, but that's accidental, not designed).
- **Stale documentation drift beyond what yesterday's audit caught:**
  - Root `README.md` still states "No implementation code exists in this repository yet."
  - `docs/PRODUCT-IMAGES-STEP-PLAN.md` still says "Status: planning only, not implemented," but the feature it plans (the wizard's "Visuals" step) has since shipped in `app/import/page.tsx` and `components/ProgressSteps.tsx`.
- **Supplier coverage is narrow relative to how it's presented.** Only Amazon and Etsy (`lib/product/suppliers/`), despite "supplier import" being framed as a general capability in the UI.
- **Zero component-level tests.** `components/` has no test files at all, despite stateful, regression-prone logic in the editor (undo/redo, autosave conflict handling, selection).
- **One known-failing leftover test.** `lib/preview/__ticker_debug.test.ts` is a debug scratch test pointing at a defunct path; it's the one failure in the current suite (687 passed / 1 failed / 3 skipped).

## 5. New feature opportunities

Building on what's already shipped; see [`docs/FEATURE-AUDIT.md`](./FEATURE-AUDIT.md) §"New feature opportunities" for the fuller original list.

**AI & content**
- Multi-variant store generation — run `content-generator.ts` N times in parallel and let the user pick a starting point instead of committing to one AI pass.
- SEO pass — meta titles/descriptions, image alt text, Product/Organization JSON-LD; nothing in `lib/ai/` touches this today.
- Competitor gap-analysis report — the competitor-scraping pipeline (`lib/product/*`) already exists for seeding a store; a second mode that surfaces "what your store is missing vs. this competitor" as a standalone report reuses the same discovery/extractor/normalizer code.

**Product Analysis**
- Replace the two placeholder checks with real signals: review count/rating can likely be scraped at import time from Amazon/Etsy pages already fetched by `lib/product/suppliers/*`; trend data needs an actual provider or a search-volume proxy via the existing `search-fallback/` web-search calls.
- Pre-publish readiness checklist — a new check pass (reusing the existing `analysis/` scoring pattern) run against the *store*, not the *product*, before "Publish to Shopify": empty sections, missing images, unwritten policy pages.

**Editor**
- Global brand kit — one settings surface for site-wide fonts/colors, on top of the existing `settings_schema.json`/`settings_data.json` resolution, instead of the current per-section magic-brush restyle.
- Mobile/tablet preview toggle in `PreviewFrame.tsx` — currently a single fixed-width iframe.
- Version diff view — `HistoryPanel.tsx` currently does all-or-nothing checkpoint restore; a JSON-diff between checkpoints would make history useful for recovering from one bad AI rewrite.

**Commerce/import**
- Multi-product catalog support — the whole pipeline (`Product`, `Project`, generation, analysis) is scoped to one product; supporting a small initial catalog is the difference between a landing-page generator and a store builder.
- More suppliers (AliExpress, CJ Dropshipping) — `lib/product/suppliers/` is already structured per-supplier and reusable.
- CSV / Shopify catalog export import — bulk path for a merchant migrating an existing catalog, bypassing per-URL scraping.

**Foundational unlock**
- Closing the auth gap is the prerequisite for client-comment mode on public preview links, agency/white-label workspaces, and safe multi-tenant use generally — nothing else in this list is safe to expose beyond a single trusted operator until it's done.

## 6. Recommended priority order

1. Add an authentication/authorization baseline (even a minimal single-user session model unblocks everything downstream).
2. Add rate limiting and an allowlist for the client-supplied `model` field on the four generation/rewrite routes.
3. Replace or clearly relabel the fake product score — either wire in real signals or stop presenting `Math.random()` as a computed metric.
4. Add the missing FK indexes (`Project.storeId`, `Store.shopifyStoreId`, `PublishRecord.projectId`).
5. Add test coverage for `lib/shopify/crypto.ts` and `lib/shopify/hmac.ts` before they see production merchant tokens.
6. Documentation hygiene pass: fix `README.md` and `docs/PRODUCT-IMAGES-STEP-PLAN.md` so they reflect current state.
